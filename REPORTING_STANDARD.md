# Reporting Standard & Schema Specifications

## 1. Reporting Principles

All outputs generated by framework agents must satisfy four foundational requirements:
1. **Machine-Readable**: Every report begins with a standardized YAML frontmatter block containing metadata, component status, timestamps, and confidence ratings, and includes structured remediation tasks.
2. **Human-Auditable**: Content following the frontmatter must be clear, well-structured GitHub-flavored Markdown with tables, code snippets, and explicit empirical evidence citations.
3. **Deterministic & Evidence-Backed**: Reports follow fixed naming conventions and strictly distinguish observed facts from inferences. "Implemented" ≠ "Migrated completely", and "Static check passed" ≠ "Runtime verified".
4. **Normal Chat & LLM Consumable**: Reports include a dedicated `## LLM REMEDIATION INPUT` section with stable task IDs so that any LLM conversation can directly consume the findings to generate safe, targeted remediation prompts.

## 3. The 10 Canonical Item Statuses

Every discovered function, hook, class, route, form, database query, cache behavior, or integration element must receive exactly one of these 10 statuses:

| Status | Definition | Next Action / Routing |
|:---|:---|:---|
| `COMPLETE` | Fully implemented in D10/D11 with verified functional equivalence and backing evidence. | Done. |
| `PARTIAL` | Partially implemented; specific sub-methods or branches remain unmigrated. | Remediation Task (Fixable from evidence). |
| `MISSING` | Discovered in D7 but completely absent in D10 target. | Remediation Task (Fixable from evidence). |
| `BLOCKED` | Cannot proceed due to an unmigrated upstream dependency or technical impediment. | Blocker Ticket (`reports/blocked/`). |
| `HUMAN_INTERVENTION_REQUIRED` | Business intent unclear, policy decision required (e.g. GDPR), or conflicting architecture. | Human Decision Gate (`reports/human_decisions/` / `reports/blocked/`). |
| `RUNTIME_UNVERIFIED` | Statically compliant, but requires live Drupal runtime/CLI execution to verify behavior (`RUNTIME_UNAVAILABLE`). | Runtime verification gate. |
| `SUPERSEDED` | Replaced by modern core functionality or modern architectural pattern. | Documented with evidence. |
| `REPLACED` | Replaced by another module, service, or external tool. | Documented with reference. |
| `OBSOLETE` | Dead code, legacy D7 compatibility shim, or unused hook with verified zero active callers. | Retired with evidence. |
| `EXCLUDED` | Intentionally excluded from scope with documented justification. | Excluded with reason. |

## 4. The 3-Path Remediation Decision Model

```
                    ANALYSIS FINDING
                           │
       ┌───────────────────┼───────────────────┐
       ▼                   ▼                   ▼
[FIXABLE FROM EVIDENCE] [REQUIRES HUMAN DECISION] [RUNTIME UNAVAILABLE]
       │                   │                   │
  Auto-Remediate    HUMAN_INTERVENTION_REQUIRED RUNTIME_UNVERIFIED
       │                   │                   │
    Re-Audit              STOP           Continue Static Work
       │                   │                   │
   Verify Fix       Decision Supplied    Live Runtime Later
                           │
                         RESUME
```

1. **Path 1: FIXABLE FROM EVIDENCE** (`MISSING` / `PARTIAL` with clear evidence)
   - The agent creates a discrete remediation task with a stable ID (`<MODULE>-<TYPE>-<NUM>`), applies the fix, and runs targeted re-validation.
2. **Path 2: REQUIRES HUMAN DECISION** (`HUMAN_INTERVENTION_REQUIRED`)
   - The agent **NEVER** invents business rules or makes policy assumptions. It halts, logs the options with evidence in `reports/human_decisions/`, and waits for a human decision before resuming.
3. **Path 3: RUNTIME UNAVAILABLE** (`RUNTIME_UNVERIFIED` / `RUNTIME_UNAVAILABLE`)
   - Static contracts and structural code are validated; runtime checks are marked `RUNTIME_UNVERIFIED` without falsely claiming completion or failing static steps.

## 5. Mandatory Report Structure

Every comprehensive audit and post-migration report MUST contain the following sections:

```markdown
# [Module/Component Name] Migration & Completeness Audit Report

## 1. Executive Summary
High-level verdict, total D7 items, migrated count, gap count, blocked count, human decision count.

## 2. Scope & Target Version
Source path, target path, Drupal core target version, execution scope (FULL_WORKSPACE vs SINGLE_MODULE).

## 3. Evidence Sources
Concrete files inspected, AST graphs, dependency graphs, test execution outputs.

## 4. Completed / Verified Items
Items with verified functional equivalence and evidence citations.

## 5. Partially Implemented Items
Items with incomplete sub-features and exact missing lines/methods.

## 6. Missing Items
D7 functional items completely absent from the D10 implementation.

## 7. Blocked Items
Items blocked by upstream dependencies with dependency chain citations.

## 8. Human Intervention Required
Items requiring engineer/business decisions with options and implications.

## 9. Runtime Unverified Items
Items requiring live execution (e.g. live database queries, cron hooks, session stores).

## 10. Superseded / Replaced Items
Items replaced by modern Drupal core or contrib services with architectural justifications.

## 11. Architectural Replacement & Behavioral Analysis
For components involving subsystem architectural replacements:
- **Architectural Replacement Analysis Table**:
  | Source Technology / Subsystem | Target Technology / Architecture | Relationship | Evidence | Status |
- **Behavioral Replacement Matrix**:
  | ID | Source Behavior | Target Behavior | Evidence | Status | Remediation |
- **Replacement Gaps**:
  Detailed classification across `MISSING`, `PARTIAL`, `BLOCKED`, `HUMAN_INTERVENTION_REQUIRED`, and `RUNTIME_UNVERIFIED`.

## 12. Obsolete & Excluded Items
Dead code, legacy D7 shims, or out-of-scope utilities with proof of zero live callers.

## 13. Remediation Tasks
Numbered list of actionable remediation tasks with stable IDs.

## 14. Dependency Analysis
Inbound and outbound dependency mappings across custom, contrib, and core modules.

## 15. Validation Requirements
Required PHPUnit tests, PHPStan levels, linting, and behavioral assertion checks.

## 16. Final Status & Verdict
Exactly one of: `PASS`, `PASS_WITH_GAPS`, `FAIL`, `BLOCKED`, `HUMAN_INTERVENTION_REQUIRED`, `UNVERIFIED`.

---

## 17. LLM REMEDIATION INPUT
Structured, copy-pasteable task specifications for consumption by standard LLM chats.
```

## 6. LLM Remediation Input Schema

The `## LLM REMEDIATION INPUT` section must present tasks in this structured YAML format:

```yaml
- task_id: "<MODULE>-<CATEGORY>-<ID>"
  status: "MISSING" # MISSING | PARTIAL | HUMAN_INTERVENTION_REQUIRED
  priority: "HIGH" # HIGH | MEDIUM | LOW
  d7_behavior: "[Detailed description of legacy D7 functionality, hook, or class]"
  d10_current_state: "[What currently exists or is missing in D10 target]"
  evidence: "reports/migration/<MODULE>/<MODULE>_GAP_ANALYSIS.md#L45"
  required_change: "[Exact architectural modification needed]"
  do_not_change: "[Existing valid D10 implementations to preserve]"
  dependencies: ["core/service_name"]
  validation: "[Exact test or verification command]"
  human_decision_required: false
```
